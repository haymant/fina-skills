# FCN Economics, Leg Allocation, and Operation Actions

## Recommendation

Add an **Economics and Payoff Composition** step to the FCN wizard. The trader enters contractual economics, while ETL/payoff compilation and native pricing generate the leg decomposition. Do not expose PV, Greeks, engine markers, or evidence fields as user-editable economics.

The canonical contracts are:

- `../../schema/ui/leg-allocation.schema.json` for funding, coupon, terminal optionality, rebate, fee, and generated pricing legs;
- `../../schema/ui/operation-action.schema.json` for logical actions, preconditions, lifecycle state gates, refresh targets, expected events, and evidence requirements;
- `../../schema/ui/ui-metadata.schema.json` for page, layout, workflow, flex-block, and renderer metadata.

## FCN economics step

Use the following wizard order for an FCN or RakiPlus-derived FCN:

```text
Product identity
→ Underlying basket
→ Coupon and observation schedule
→ Protection and knock-in/knock-out
→ Economics and payoff composition
→ Settlement
→ Pricing configuration
→ Review and submit
```

The economics step should contain four semantic flex blocks:

```text
Economics and payoff composition
├── Funding
├── Coupon
├── Terminal optionality
└── Generated leg preview
```

### Funding

Funding captures contractual principal behavior, not an independently tradeable bond. Render nominal, currency, return ratio, maturity, settlement mode, and denomination where applicable. The user may edit these terms. Funding PV and discounting provenance are generated by the pricing request and result.

### Coupon

Coupon captures fixed or range-accrual economics. For RakiPlus-derived FCN, include coupon rate, accrual rate, frequency, observation cadence, accrual indicator, range bounds, coupon barrier, memory behavior, KO coupon, payment lag, and denomination rounding where the product contract supports them. The user enters terms; `N1`, `N2`, accrued amount, coupon PV, and fixing provenance are derived.

### Terminal optionality

Use the label **PUT / Terminal Optionality** rather than assuming every residual is a vanilla put. Capture the basket indicator, strike, KI barrier, monitoring style, participation, cap/floor, settlement method, and product-specific KI/non-KI branches. The terminal payoff graph and PV are generated, not manually entered.

## Editable versus generated fields

| Field | Editable in economics step | Generated or read-only |
|---|---:|---:|
| Notional, currency, return ratio | Yes | No |
| Coupon, ranges, barriers, strikes | Yes | No |
| Payment and observation schedules | Yes or schedule-generated | Schedule expansion and fixing status |
| `N1` and `N2` | No | Yes |
| Funding, coupon, put/terminal PV | No | Yes |
| Greeks and scenario values | No | Yes |
| Engine marker and evidence status | No | Yes |
| Payoff graph node IDs | No | Yes |

The UI may show declared leg roles before pricing. Once compiled, it should show `origin: compiled_payoff` and after pricing `origin: pricing_engine`, together with source paths and evidence.

## Leg preview

Render the generated decomposition as a read-only rich list or property grid:

```text
FUNDING   Principal return at maturity or KO     declared / priced
COUPON    Fixed or range-accrual coupon          compiled / priced
PUT       Conditional worst-of terminal residual compiled / priced
```

Every row should expose the role, description, lifecycle condition, payment schedule, source term paths, payoff graph node, PV, currency, and evidence status. A decomposition is an explainability and reconciliation view; it does not claim that the product is legally a static portfolio of three independent instruments.

## Action metadata

Actions represent user intent and registered logical operations. They do not authorize a transition. The server action must authenticate the actor, validate the input schema, resolve the operation, enforce lifecycle state and capability, invoke the configured adapter, normalize the result envelope, and refresh declared resources.

For pricing, use separate operations such as `quote.price` and `quote.reprice`. For persistence and lifecycle, keep `quote.persist`, `trade.accept`, `trade.amend`, `trade.cancel`, and `trade.knock` distinct. Do not attach an ambiguous `submit` action to the entire wizard.

An action contract should declare:

```yaml
id: trading.fcn.quote-price
action_schema: ../../schema/ui/operation-action.schema.json
operation: quote.price
process: fcn-termsheet-quote
input_schema: pricing-request
result_schema: fcn-native-pricing-result
record_binding: /rfq
confirmation_policy: never
preconditions:
  - path: /lifecycle_state
    operator: in
    value: [draft, ready_for_pricing]
actor_capability: trading.quote.price
refresh_targets: [rfq.detail, quote.list, lifecycle.timeline]
expected_events: [quote.priced]
evidence_required: true
argument_bindings:
  - input_path: /
    argument_path: /pricing_request
    required: true
```

Destructive or legally meaningful actions must declare an appropriate confirmation policy. Routine pricing, draft save, and read-only refresh actions normally use `never`; trade acceptance, cancellation, or a knock operation should use `when_destructive` or `always` according to the lifecycle contract.

## Runtime rules

The React runtime should load domain schema, UI metadata, workflow metadata, action metadata, and leg-allocation metadata independently. It should resolve renderer hints, validate editable fields with React Hook Form and AJV, and preserve JSON Pointer paths in errors and source references.

The browser must never choose an MCP tool, engine, repository, or credential. It invokes a named server action. The server resolves `quote.price` through the model registry and process contract. The UI displays the resulting engine marker and evidence manifest but cannot claim production evidence from schema validation alone.

The final submission path is:

```text
editable FCN terms
→ terms projection
→ ETL augment and compile
→ payoff graph and leg allocation
→ pricing request
→ native quote/reprice
→ generated leg PVs and provenance
→ quote persistence or trade acceptance
→ lifecycle event and refresh
```
